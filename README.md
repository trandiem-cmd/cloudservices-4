# Week 6 Assignment – CI/CD and Observability

## 1. Overview

This assignment extends the multi-container application developed in the previous weeks by implementing CI/CD automation and basic observability.

The main objectives were:

* Automate application build and deployment using GitHub Actions.
* Build and push a Docker image to GitHub Container Registry (GHCR).
* Automatically deploy the application to Rahti/OpenShift.
* Configure liveness and readiness probes.
* Implement structured logging in the backend.
* Use OpenShift commands to verify application health and logs.

---

## 2. CI/CD Pipeline

The CI/CD pipeline is implemented using GitHub Actions.

### Pipeline Flow

```text
Push code to GitHub
        ↓
GitHub Actions triggered
        ↓
Checkout source code
        ↓
Build Docker image
        ↓
Push image to GHCR
        ↓
Login to Rahti/OpenShift
        ↓
Update deployment
        ↓
Deploy application
        ↓
Verify running Pod
```

### Main Pipeline Steps

1. **Trigger**
   The workflow is triggered when code is pushed to the `main` branch.

2. **Checkout**
   `actions/checkout@v4` downloads the repository source code to the GitHub Actions runner.

3. **Build Docker Image**
   The frontend Docker image is built using the repository root as the Docker build context.

4. **Push Image**
   The image is pushed to GitHub Container Registry using the `REGISTRY_TOKEN` GitHub secret.

5. **Deploy to Rahti**
   GitHub Actions logs in to OpenShift using `RAHTI_TOKEN` and `RAHTI_SERVER`, then applies the Kubernetes deployment configuration.

6. **Verification**
   The deployment and running Pods are checked using OpenShift commands.

### Example Image

```text
ghcr.io/trandiem-cmd/cloudservices-4/webpage:<commit-sha>
```

Using the Git commit SHA as the image tag makes it possible to identify which source version was deployed.

## 3. CI, Continuous Delivery and Continuous Deployment

| Concept                     | Description                                                                                                                                |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Continuous Integration (CI) | Developers frequently integrate code changes, followed by automated building and testing.                                                  |
| Continuous Delivery         | The application is automatically built and tested and kept ready for release, usually with a manual approval before production deployment. |
| Continuous Deployment       | Validated changes are automatically deployed without requiring a manual deployment step.                                                   |

In this assignment, the GitHub Actions workflow builds the image, pushes it to the registry, and automatically deploys it to Rahti. Therefore, the workflow demonstrates characteristics of **Continuous Deployment**.

## 4. Deployment Automation

The assignment uses an imperative CLI deployment approach.

```text
GitHub Actions
      |
      | oc login
      v
Rahti / OpenShift
      |
      | oc apply
      v
Deployment
      |
      v
Pod
```

The CI workflow directly connects to the OpenShift cluster and applies the deployment configuration.

The main security consideration is that the CI system needs an OpenShift credential with sufficient permissions. Therefore, credentials such as `RAHTI_TOKEN` are stored as GitHub repository secrets rather than being written directly in the workflow.

## 5. Observability

Observability helps determine the internal state and behaviour of an application from the information it produces.

The three main pillars are:

| Pillar  | Description                                                                                                 | Example Question                                                              |
| ------- | ----------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Metrics | Numerical measurements collected over time, such as CPU usage, request rate, error rate, and response time. | Is the application experiencing a high error rate or increased response time? |
| Logs    | Records of events generated by the application or system.                                                   | What exactly happened when this request failed?                               |
| Traces  | Records the path of a request across multiple services and the time spent in each component.                | Which service is causing this request to be slow?                             |

## 6. Liveness and Readiness Probes

The frontend Deployment was configured with both liveness and readiness probes.

```yaml
livenessProbe:
  httpGet:
    path: /
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 15

readinessProbe:
  httpGet:
    path: /
    port: 8080
  initialDelaySeconds: 5
  periodSeconds: 15
```

### Liveness Probe

The liveness probe checks whether the container is still functioning. If the liveness check repeatedly fails, OpenShift can restart the container.

### Readiness Probe

The readiness probe checks whether the application is ready to receive traffic. If the readiness check fails, the Pod can remain running but is removed from the Service endpoints.

### Readiness Probe Failure Test

To test the readiness probe, the port was temporarily changed from `8080` to a non-existent port:

```yaml
readinessProbe:
  httpGet:
    path: /
    port: 1234
```

The Pod remained in the `Running` state but became:

```text
READY   0/1
```

This demonstrated that a failed readiness probe prevents the Pod from receiving traffic without necessarily restarting the container.

After the test, the readiness probe was restored to port `8080`.

## 7. Structured Backend Logging

Structured logging was added to the Flask backend.

The backend records information about each HTTP request in JSON format, including:

* HTTP method
* Request path
* Response status
* Response time

Example:

```json
{
  "method": "GET",
  "path": "/api/health",
  "status": 200,
  "responseTimeMs": 1.42
}
```

The logs can be inspected using:

```bash
oc logs <backend-pod-name>
```

This makes the backend logs easier to search and analyse because each request has clearly defined fields.

## 8. Testing Backend Logs

A request can be generated using the backend API, for example:


The backend Pod logs can then be checked with:


The expected output contains the request path, HTTP method, status code, and response time.

## 9. Problems Encountered and Solutions

### 9.1 GHCR Image Pull Failure

Initially, OpenShift could not pull the container image from GitHub Container Registry because the package was private.

The problem was indicated by an `ImagePullBackOff` state.

**Solution:**
The GHCR package visibility was changed to public so that the OpenShift cluster could pull the image without requiring an additional image pull secret.

---

### 9.2 Docker Build Context Problem

The Dockerfile was located inside the `frontend` directory, while it referenced files using paths such as:

```dockerfile
COPY frontend/nginx.conf /etc/nginx/nginx.conf
```

Building from the `frontend` directory caused the required files to be outside the Docker build context.

**Solution:**

```bash
docker build -t <image-name> -f frontend/Dockerfile .
```

The repository root was used as the build context.

---

### 9.3 Readiness Probe Typo

The readiness probe initially contained a spelling error:

```yaml
readnessProbe:
```

It was corrected to:

```yaml
readinessProbe:
```

After applying the corrected deployment, OpenShift recognised the readiness probe correctly.

---

### 9.4 Testing a Failed Readiness Probe

A non-existent HTTP path did not produce the expected failure because the Nginx configuration returned a successful response.

**Solution:**
A non-existent port (`1234`) was used instead. This caused the readiness probe to fail and demonstrated that the Pod could remain `Running` while becoming `Not Ready`.

## 11. Reflection

This assignment provided practical experience with the relationship between Docker, GitHub Actions, and OpenShift. The CI/CD pipeline demonstrated how a source-code change can automatically result in a new container image and deployment.

The observability tasks also showed that application health is not only about whether a container is running. Liveness and readiness probes provide different types of health information, while structured logs provide useful details about individual requests.

The troubleshooting process was particularly useful because it demonstrated real deployment issues such as registry permissions, Docker build contexts, Kubernetes configuration errors, and health-check failures.
