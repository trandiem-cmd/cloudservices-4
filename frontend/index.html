1. Explain the difference between SAML and OAuth. When would a company choose one over the other ?:

1.1. Explain the difference between SAML and OAuth.

The main difference is that SAML focuses on verifying a user’s identity and enabling SSO, while OAuth focuses on granting applications controlled access to resources. SAML is commonly used in enterprise environments, whereas OAuth is widely used for web applications, mobile applications, and API-based services.

SAML and OAuth are security standards that serve different purposes:

- SAML (Security Assertion Markup Language) is primarily used for authentication and Single Sign-On (SSO). It allows an identity provider to verify a user’s identity and provide access to different applications without requiring the user to log in separately to each one.

- OAuth is primarily an authorization framework. It allows an application to access specific resources on behalf of a user without requiring the user to share their password. For example, an application can use OAuth to access a user’s data through an API with the user’s permission.

1.2 When would a company choose one over the other ?

A company would choose between SAML and OAuth depending on its security and application requirements.

SAML is mainly used for authentication and Single Sign-On (SSO), making it suitable for large organizations such as governments, healthcare institutions, and enterprises that need centralized access control for many users and sensitive data. It is especially common in enterprise and browser-based environments.

OAuth is primarily designed for authorization. It allows applications to access specific user resources without requiring the user's password. OAuth is therefore more suitable for modern web and mobile applications, APIs, and situations where flexible access and user experience are important. OAuth relies on HTTPS/TLS to protect communication.

SAML is generally preferred for enterprise authentication and SSO, while OAuth is preferred for delegated authorization and resource access.

Source: https://www.fortinet.com/resources/cyberglossary/saml-vs-oauth

2. What is a Web Application Firewall (WAF) and what kinds of attacks does it defend against? Where would you place one in the three-container architecture you built in Week 4 (Route -> frontend -> backend -> db)?:

2.1 What is a Web Application Firewall (WAF)?

A Web Application Firewall (WAF) protects web applications by filtering and monitoring HTTP traffic between the application and the Internet. It can defend against common attacks such as Cross-Site Scripting (XSS), Cross-Site Request Forgery (CSRF), file inclusion, and SQL injection. A WAF operates at Layer 7 (Application Layer) of the OSI model and is not designed to protect against every type of attack, so it is usually combined with other security measures. It acts as a reverse proxy, placing a layer of protection between clients and the web server. WAF protection is based on security rules or policies that identify and block malicious traffic. These policies can also be quickly modified to respond to new threats, such as applying rate limiting during a DDoS attack.

Source: https://www.cloudflare.com/learning/ddos/glossary/web-application-firewall-waf/

2.2 What kinds of attacks does it defend against?

A WAF can help protect against common web attacks such as:

- SQL Injection (SQLi): malicious SQL commands inserted into application requests.

- Cross-Site Scripting (XSS):injecting malicious scripts into web pages.

- Path Traversal:attempting to access files or directories outside the intended application directory.

- Command Injection: attempting to execute unauthorized commands on the server.

- HTTP request attacks: such as malicious or malformed requests designed to exploit web applications.

2.3 Where would you place one in the three-container architecture you built in Week 4 (Route -> frontend -> backend -> db)?

User → WAF → Route → Frontend → Backend → Database

The WAF should generally be placed before the application traffic reaches the frontend

The WAF acts as the first security layer, inspecting incoming HTTP/HTTPS requests and blocking suspicious traffic before it reaches the application containers. This placement allows it to protect the frontend and, indirectly, the backend and database from attacks originating through web requests. However, a WAF is not a replacement for application-level security. Authentication, input validation, access control, and secure database practices should still be implemented within the application itself.

3. Describe how a decentralized or cooperative storage network (for example Sia or IPFS) differs from centralized object storage such as Allas or Amazon S3. What are the trade-offs ?

3.1 Describe how a decentralized or cooperative storage network (for example Sia or IPFS) differs from centralized object storage such as Allas or Amazon S3.

The main difference is how data is stored and managed.

In a decentralized or cooperative storage network, data is distributed across multiple nodes rather than being controlled by a single storage provider. This can reduce dependence on one organization and provide greater decentralization, but performance and availability may depend on the participating nodes.

Centralized object storage such as Allas or Amazon S3 is operated by a specific provider. The provider manages the infrastructure, replication, availability, and access control, making it generally easier for organizations to manage and integrate into applications.

The key distinction is that decentralized storage distributes responsibility across multiple participants, whereas centralized object storage relies on a single provider to manage the storage infrastructure.

3.1 What are the trade-offs ?

The main trade-offs between decentralized/cooperative storage and centralized object storage are related to control, performance, reliability, cost, and complexity.

Decentralized storage provides greater distribution and reduces dependence on a single provider, but may introduce more complexity and less predictable performance. Centralized storage is generally easier to manage and provides more predictable performance and availability, but users depend more heavily on the provider and its infrastructure.

4. What is YAML and why has it become the default configuration format for Kubernetes/Rahti manifests? Compare it briefly to JSON.

4.1 What is YAML ?

Kubernetes is dependent on YAML (YAML Ain't Markup Language) as its configuration language. YAML makes managing and deploying Kubernetes more easy and simple. In this article, we'll cover all the aspects of using YAML in Kubernetes.

4.2 Why has it become the default configuration format for Kubernetes/Rahti manifests?

ML is widely used in Kubernetes/Rahti because it provides a simple and readable way to declaratively describe application configurations and infrastructure resources.

- Human-readable: Simple syntax using indentation and key-value pairs, making configurations easy to read and edit.

- Expressive: Supports nested structures, lists, and comments, which are useful for defining complex Kubernetes resources.

- Easy to maintain: Its clear structure makes configurations easier to organize, update, and troubleshoot.

- Community standard: Widely adopted by Kubernetes, so there are many examples, tutorials, and documentation available.

- Good tooling: Editors provide features such as syntax highlighting, autocompletion, and validation.

Source: https://www.geeksforgeeks.org/devops/what-is-yaml-in-kubernetes/

4.3 Compare it briefly to JSON.

- Readability: YAML is generally easier for humans to read because it uses indentation; JSON uses braces {} and brackets [].

- Syntax: YAML has simpler and less verbose syntax, while JSON requires more punctuation such as quotes and commas.

- Comments: YAML supports comments; standard JSON does not.

- Structure: Both can represent nested data, lists, and key-value pairs.

- Kubernetes: YAML is preferred because Kubernetes manifests are easier to read, write, and maintain in YAML.

Source: https://aws.amazon.com/compare/the-difference-between-yaml-and-json/
