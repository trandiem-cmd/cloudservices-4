PART A: ANSWER THE QUESTIONS:

1. Explain the difference between Continuous Integration, Continuous Delivery and Continuous Deployment.

- Continuous Integration (CI) focuses on frequently integrating code changes into a shared repository and automatically building and testing the code to detect problems early.

- Continuous Delivery automates the build, testing, and preparation of validated code so that the application is always in a releasable state.

- Continuous Deployment goes one step further: changes that pass the automated tests are automatically deployed to production without a manual approval step.

Aspect Continuous Integration (CI) Continuous Delivery (CD) Continuous Deployment (CD)
Main purpose Integrate code changes frequently Keep the application ready for release Automatically deploy changes to production
Main activities Merge code, build, and run automated tests Build, test, and prepare validated code for release Automatically release and deploy validated changes
Automation level Automates integration, build, and testing Automates the delivery process but may include a manual approval Fully automates deployment after successful tests
Production deployment Not the main focus Usually requires a manual approval or release step Automatically deployed without manual approval
Goal Detect integration problems early Keep software in a releasable state Deliver new changes to users as quickly as possible

2. Describe the structure of a GitHub Actions workflow (triggers, jobs, steps). What would a minimal pipeline for the app you built in Week 4/5 need to do?:

2.1. A GitHub Actions workflow: is defined in a YAML file and consists mainly of triggers, jobs, and steps.

- Triggers: Events that start the workflow, such as a push to the main branch or the creation of a pull request.

- Jobs: Groups of tasks that GitHub Actions executes on a runner. Jobs can run sequentially or in parallel.

- Steps: Individual actions or commands executed within a job, such as checking out source code, building an image, or deploying an application.

3. Compare the three deployment-automation patterns discussed (imperative CLI step, ImageStream trigger, GitOps). What are the security trade-offs of each, particularly around who holds cluster credentials?

The three deployment-automation patterns differ mainly in how the deployment is triggered and where the cluster credentials are stored.

- Imperative CLI step: The CI pipeline directly connects to the OpenShift cluster and runs commands such as oc apply. This approach is simple and easy to implement, but the CI system must hold cluster credentials. Therefore, if the CI credentials are compromised, an attacker may be able to directly modify the cluster.

- ImageStream trigger: In this approach, OpenShift monitors an ImageStream and automatically starts a deployment when a new image is available. This reduces the need for the CI pipeline to have direct cluster access. However, access to the container registry and ImageStream must be protected because an unauthorized image update could trigger a deployment.

- GitOps: The desired cluster configuration is stored in a Git repository, and a GitOps controller inside the cluster applies the changes. The cluster credentials are therefore held by the controller rather than the CI pipeline. This provides stronger separation between CI and cluster access, although it requires more infrastructure and configuration.

The security trade-offs:

The main security trade-off is therefore where the authority to change the cluster is located. The imperative CLI approach gives more direct control to the CI system, while ImageStream and GitOps can reduce direct cluster access from CI. GitOps provides the clearest separation of responsibilities, but also introduces additional complexity.

4. What are the three pillars of observability (metrics, logs, traces)? Give an example of a question each one is best suited to answer.

Pillar Description Example question it answers best
Metrics Numerical measurements collected over time, such as CPU usage, request rate, error rate, and response time. “Is the application experiencing a high error rate or increased response time?”
Logs Records of events generated by the application or system, such as requests, errors, status codes, and messages. “What exactly happened when this request failed?”
Traces Records the path of a request across different services and shows how much time is spent in each component. “Which service is causing this request to be slow?”
